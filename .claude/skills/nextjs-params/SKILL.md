# Next.js Route Params Typing Convention

When working with route params in this project, always use the generated Next.js helper types. Never manually type params inline.

## Convention: Define a named type alias above the component

Always define the props/params type as a separate `type` alias before other types and before the component. This keeps the route string in one place and makes the component signature clean.

## Server Components

Use `PageProps` or `LayoutProps` with the route string literal:

```tsx
type ChatPageProps = PageProps<'/[project-id]/(chat)/[chatId]'>;

export default async function ChatPage({ params }: ChatPageProps) {
    const { chatId, 'project-id': projectId } = await params;
}
```

```tsx
type ProjectLayoutProps = LayoutProps<'/[project-id]'>;

export default async function ProjectLayout({ children, params }: ProjectLayoutProps) {
    const { 'project-id': projectId } = await params;
}
```

## Client Components

Use `useParams` with a named `PageParams` type alias (defined globally in `types.d.ts`):

```tsx
type ChatPageParams = PageParams<'/[project-id]/(chat)/[chatId]'>;

export default function ChatPage() {
    const { chatId, 'project-id': projectId } = useParams<ChatPageParams>();
}
```

`PageParams<T>` extracts the resolved (non-Promise) params type from `PageProps<T>`, so server and client components always share the same param types.

## Rules

- Always define a named type alias (e.g. `type ChatPageProps = PageProps<'...'>;`) above the component — never inline the generic directly in the function signature or `useParams` call
- Never type params manually (e.g. `{ 'project-id': string; chatId: string }`)
- Never use `useParams()` without a generic — always pass a named `PageParams` type alias
- Never define custom param interfaces per-page — the route string literal is the single source of truth
- These types are generated by `next dev` / `next build` / `next typegen` — if they're missing, run one of those first
